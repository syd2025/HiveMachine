# 复刻开源项目：协议层 + 真实资金场景专项补充（个人开发者适用）

本文是《复刻开源项目：方法论与 SDD 文档体系》和《AI Coding 执行手册》的扩展,专门覆盖一种更高风险的场景组合:**复刻对象包含协议/共识层,且最终打算处理真实用户资金,由个人独立开发者主导**。

这个组合相比普通应用级复刻,多出两类此前文档没有覆盖的风险:**共识/协议层的灾难性失败模式**,以及**单人开发在关键安全环节上缺乏交叉校验**。本文的核心是补一道前两份文档都没有的硬性关卡,并说明个人开发者应该如何调整现实预期和分工方式。

---

## 一、范围扩展:解构对象不再只是应用层

按照执行手册阶段一的做法,解构对象需要从 openmayhem 单一仓库,扩展到 Trac Network 生态下与共识/结算相关的仓库组合。这一步优先级最高,因为不搞清楚协议层的真实边界,后面所有工作都建立在错误的范围假设上。

### 1.1 具体动作

- [ ] 列出 Trac Network 生态中,openmayhem 实际依赖的协议层仓库清单(MSB、Trac Peers、合约、以及 openmayhem 自身 vendored 的 `intercom/` 子树),逐个标注:是完整开源、部分开源,还是只有客户端代码、服务端/验证者逻辑不公开
- [ ] 对每个协议层仓库,单独走一遍执行手册阶段一的"行为规格提取"流程——协议层的规格提取比应用层更依赖读懂共识算法本身,不能只看接口签名
- [ ] 明确区分:协议层里哪些是"确定性状态机逻辑"(相对容易复刻和验证)、哪些是"网络层博弈/激励设计"(即使代码复刻对了,参数设计不当也可能导致经济攻击,这部分几乎没法只靠"读代码"验证正确性)

### 1.2 一个必须现实面对的判断

- [ ] 是否已经评估过:协议层中是否存在验证者准入机制、惩罚(slashing)机制、或需要跨节点博弈才能验证正确性的部分——如果有,这部分**无法**通过"个人在本地跑通单元测试"来确认安全,必须依赖阶段三之后新增的审计关卡

## 二、强制关卡:真实资金上线前的独立第三方审计

这是本文最核心的新增内容。**在执行手册原有的五阶段流程之后,真实资金上线前必须插入这道关卡,且不可用"我自己反复 review 过了"或"AI 帮我做了安全检查"来替代。**

### 2.1 为什么这道关卡不可替代

人工 review 和 AI 辅助检查能发现的问题类型,和独立第三方审计能发现的问题类型,系统性地不同:

- 开发者(包括你自己 review 自己的代码)容易被自己最初的设计假设"锁死"——你不会去测试你根本没想到的攻击路径,因为如果你想到了,通常一开始就会规避
- AI 辅助的安全检查,基于的是训练数据里已知的漏洞模式,对于**这个具体协议参数组合、这个具体经济设计**下才会出现的新型攻击路径,识别能力有限
- 独立审计的价值恰恰在于"审计者没有你的设计路径依赖",更容易用对抗性思维去构造你没想过的场景

### 2.2 审计应该覆盖的范围

- [ ] 共识/状态机核心逻辑(账本状态转移、验证者/节点间的一致性保证)
- [ ] 资金相关的合约代码(Solidity 部分,涉及链上结算的路径)
- [ ] 支付/结算的信任边界(Stripe webhook 验签、链上存款确认、跨 rail 结算的账目一致性)
- [ ] 密钥管理与签名逻辑(尤其是本地钱包、mnemonic 生成与存储)
- [ ] 经济激励设计的博弈稳定性(是否存在低成本攻击能让攻击者持续获利的路径)——这一项如果审计机构不擅长经济学分析,可能需要单独找人做博弈论/机制设计层面的复核,不要假设"代码审计"自动覆盖了"经济设计审计"

### 2.3 审计前需要准备的材料

- [ ] 完整的行为规格文档(执行手册阶段一产出),让审计方不需要从零逆向你的代码就能理解设计意图
- [ ] 《原始项目解构记录》和《偏离决策日志》,让审计方知道哪些地方你是刻意偏离原设计的,重点复核这些偏离点(偏离原设计的地方往往是新引入 bug 概率最高的地方)
- [ ] 完整的对照测试套件和运行结果,证明基础功能层面已经过自我验证,审计资源可以集中在测试覆盖不到的对抗性场景上
- [ ] 一份明确的"信任假设清单"——你的系统假设了哪些前提成立(比如"多数验证者诚实""Stripe webhook 不会被伪造"),审计方会重点检查这些假设是否真的站得住

### 2.4 现实提醒(不确定的部分,请自行核实)

审计的具体费用、周期、机构选择,和项目规模、代码量、审计范围深度密切相关,我不掌握可靠的当前报价信息,不应该给你一个具体数字造成误导。建议:

- [ ] 直接联系 2-3 家专注区块链/协议安全审计的机构,拿实际报价和周期估算,再倒推你的时间表和预算是否现实
- [ ] 不要把审计当作"上线前最后一步临时插入的任务"来预算时间——协议层审计经常会发现需要返工的问题,返工后可能需要复审,这个来回本身要计入时间表

## 三、个人开发者的现实调整

在"必须一步到位复刻完整协议层"这个目标下,单人开发在某些环节结构性地缺乏交叉校验能力。以下是具体建议,而不是泛泛的"找人帮忙"。

### 3.1 哪些环节必须引入外部协作,不能单人推进

- [ ] **共识核心逻辑的设计评审**:即使不请全职团队,建议在设计定稿后(写代码之前),找至少一位有分布式系统/密码学背景的人过一遍设计文档,而不是等代码写完了才审——设计阶段的缺陷,审代码时往往已经很难发现根源
- [ ] **最终的资金/合约相关代码**:第三方审计是硬性要求,前面已说明,这里不重复
- [ ] **经济参数设计**(手续费率、惩罚力度、准入门槛等):这类参数设计错了,代码逻辑完全正确也会导致系统被"合法地"套利耗尽,建议找人做压力推演,而不只是审代码

### 3.2 单人可以独立推进、但要延长验证周期的环节

- [ ] 应用层(openmayhem 本身的 CLI、网关、路由逻辑)可以按执行手册的常规流程,单人 + AI coding 推进
- [ ] 测试网验证阶段建议比普通项目更长——不是"跑几天没问题就上线",而是尽量引入外部使用者(哪怕是朋友、社区里愿意帮忙测试的人)在测试网上真实使用一段时间,单人自己测试很难覆盖"别人会怎么用/怎么误用"的场景

### 3.3 一个诚实的预期管理

- [ ] 建议明确写下一个"如果做不到位就暂不接入真实资金"的止损线,而不是把"未来上线"当作既定计划、只是时间早晚问题。协议层安全性没有做到位时暂缓上线,代价是时间;做到位前就上线出问题,代价是用户真实资金损失和你自己的法律责任——这两者不是同一量级的风险

## 四、合规提醒(非法律意见)

处理真实用户资金、涉及法币支付(Stripe)和跨境加密结算,在很多司法辖区可能触发需要牌照或注册的"支付服务/资金转移"相关监管要求。这一块我不是律师,给不了准确判断,也不应该假装可以。

- [ ] 在真实资金接入用户前,建议找熟悉你所在司法辖区金融科技/加密监管的律师做一次合规评估,而不是假设"开源项目怎么做我照着做就没事"——原项目(Trac Systems UG)的合规安排(比如它注册在哪个法域、以什么身份运营)不会自动适用于你的复刻版本

## 五、更新后的完整流程

结合执行手册原有五阶段,加入本文新增内容后,完整流程如下:

```
【应用层】执行手册阶段一~五（可个人+AI推进）
    ↓
【协议层】本文一~二节的解构与设计评审（需要外部协作）
    ↓
长期测试网验证（尽量引入外部真实使用者）
    ↓
【硬性关卡，不可跳过】独立第三方安全审计（协议层+资金路径）
    ↓
审计发现问题 → 修复 → 视情况复审
    ↓
【建议关卡】合规评估（视你所在司法辖区）
    ↓
小范围灰度上线，资金规模严格设限
    ↓
逐步放开
```
